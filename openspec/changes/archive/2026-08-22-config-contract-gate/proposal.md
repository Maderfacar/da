# Config Contract Gate — 設定寫錯的上不了線（承諾 1）

> 承諾順序 2 → 1 → 3，承諾 2（`login-health-observability`）已上 prod `1bd8f7c`，本變更為承諾 1。
> 交付形態：**3 個 Phase（A 契約 / B build gate / C 執行期健檢）**，可獨立上 prod。

## Why

2026-08-19 手機瀏覽器登入 100% 失敗，根因是 `NUXT_LINE_LOGIN_CHANNEL_ID=2009509209` 被 Nitro 的
`destr()` 轉成 number，而程式碼用 `as string` 斷言後直接與字串比對。兩個結構性缺口：

1. **設定值零驗證**：專案沒有 `server/plugins/`、server 端零 `zod`。設定的型別靠 `as string`
   這種「宣稱」而非「驗證」——宣稱不會在錯的時候報錯。
2. **沒有任何一道關卡會因為設定錯而擋下部署**。錯誤設定可以一路安靜地上 prod，然後由使用者發現。

主流做法是啟動時就檢查每一個設定的型別與格式，錯了直接開不起來。本變更補上這件事。

## What Changes

三道關卡，各自涵蓋不同的失效時機：

| 關卡 | 時機 | 涵蓋 |
|---|---|---|
| **build gate** | 部署前 | 值的格式錯誤、必要設定缺失、**destr 型別陷阱的靜態掃描** |
| **執行期健檢端點** | 部署後、持續 | prod 實際狀態（build 時看不到的、或部署後被改動的） |
| **CI 定時呼叫** | 每小時 | 設定漂移（有人改了 Vercel 環境變數） |

### 關鍵設計：destr 陷阱要用靜態掃描擋，不是靠型別

build 期讀到的 `process.env` 永遠是字串，**看不出 destr 之後會變成什麼**。真正要防的是
「純數字設定被當字串比對」。因此 build gate 對標記為 `numeric-id` 的設定做靜態掃描：
凡直接 `config.<key>` 讀取而未經 `configStr()` 包裹者一律擋下。這正是 `4ce6071` 那顆的形狀。

### 已鎖定的決策

| 項目 | 決策 | 理由 |
|------|------|------|
| 契約單一真相 | `shared/env-contract.mjs`（純 JS + JSDoc） | 必須同時被 Nitro 端點與「編譯前執行」的 node 腳本引用；兩份契約會漂移，正是這類 bug 的來源 |
| build gate 硬擋範圍 | **格式錯誤** + **destr 靜態掃描** + **核心必要設定缺失** | 前兩者不可能擋掉本來就正常的部署；第三項只含「缺了站台本來就是壞的」項目 |
| 非核心設定缺失 | **警告，不擋** | `.env.dev` 只有 23 個 key、缺 P29 雙 channel 那組，**不是 prod 的可靠鏡像**。把無法查證的項目設成硬擋，會擋掉本來正常的部署 |
| prod 實際狀態 | 由執行期健檢端點回報，不猜 | 待端點回報後，再把確認存在的項目逐一升級為硬擋 |
| 健檢端點保護 | 沿用 `CRON_SECRET` Bearer | 與既有 cron 端點同範式，不新增機制 |
| 端點輸出 | **只回名稱與狀態，永不回值** | 設定值多為憑證 |

### 驗收標準

> **把 `NUXT_LINE_LOGIN_CHANNEL_ID` 改成錯誤格式，`pnpm build` 必須是紅的、部署必須失敗。**
> **把某處 `configStr()` 拿掉改回直接讀取，build 同樣必須是紅的。**

## Non-goals

- **不引入 zod 到 server**：契約只需要「必填 + 格式 + 型別危害」三種判斷，正規表達式已足夠；
  為此加一個 runtime 相依不划算，且 build gate 需在編譯前以純 node 執行。
- **不做啟動時 crash**：Nitro plugin 啟動失敗會讓整站（含公開頁）500。擋在部署前 + 執行期回報，
  比讓 prod 掛掉更符合「上不了線」的原意。
- **不改任何既有設定值或讀取行為**：本變更只加檢查。
